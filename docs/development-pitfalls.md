## 1. 使用方式

本文是后续开发的“错题本”。遇到消息一致性、会话切换、滚动、媒体、原生窗口、已读状态或性能问题时，先按症状查找对应条目，再阅读列出的最终契约和回归门禁。不要直接复制某个中间提交的补丁：历史上多次出现“局部症状消失，但状态所有权、异步生命周期或几何边界仍未解决”的情况。

每个条目区分五件事：

1. **症状**：用户实际看到的错误。
2. **错误模型**：实现为什么必然或高概率异常。
3. **反复过程**：哪些提交尝试过修复、哪些方案被撤回或后来取代。
4. **最终修复**：审阅产品基线使用的状态模型、算法或平台能力。
5. **防复发规则**：后续修改必须保持的不变量和测试。

证据优先级如下：提交差异与当前代码 > 自动化测试 > `project.md`/专题文档 > 提交标题。文档与代码冲突时以代码和测试为准，并在本轮同步修正文档。

## 3. 顽疾一：缓存历史丢失、误删与启动覆盖

**状态：已修复。核心提交：** `2f702f9`、`d2730bd`、`e814886`、`4f54163`、`41b4f01`、`d65bba9`。

### 3.1 症状与错误模型

- 缓存首屏出现后，初始同步或较短的服务端窗口会让旧消息消失。
- TDLib 仅从本地缓存驱逐消息时，前端把 `updateDeleteMessages` 当作服务端永久删除。
- 使用“已确认窗口的最老/最新 ID”推断中间未返回的缓存消息已被删除；当窗口不完整、分页重复或消息同秒发送时会误删或错序。
- 授权状态刚变为 ready、连接仍在 syncing/offline 时立即拉历史，用不完整结果覆盖已经可读的快照。
- 每个文件进度、头像或消息小更新都触发完整快照序列化、跨 IPC 传输和 DPAPI 写盘，反过来阻塞消息呈现。

### 3.2 反复过程

`d2730bd` 先在 Store 层保留缓存历史，`e814886` 又为分页停滞与回复水合增加保护；但只要仍从不完整窗口推断删除，丢失仍会复现。`4f54163` 才移除范围推断：缓存 ID 只在服务端明确确认相同 ID 时退出 pending 集合，并忽略 `from_cache=true && is_permanent!=true` 的删除更新。`41b4f01` 继续把历史加载约束到 connection=online，避免启动同步覆盖。`d65bba9` 最终处理写入侧卡顿，把大快照改成分块事务与合并调度。

### 3.3 最终修复技术

- Telegram/TDLib 是事实源；本地快照只提供首屏和离线恢复，不推断远端删除。
- 永久删除只接受明确的永久事件；本地缓存驱逐不转成产品删除。
- 消息先按时间排序，同秒消息再用可解析的 TDLib `BigInt` ID 稳定排序。
- 历史分页按会话维护游标、连续停滞计数和 hasMore，不以单个重复页草率宣告耗尽。
- 启动阶段只有 authorization=ready 且 connection=online 才加载历史；恢复在线后再触发 active chat/topic 刷新。
- 快照写入使用随机事务 ID，数组按 64 项分块通过 IPC 发送，每块后让出主线程；Rust 端限制并发暂存事务并只在 commit 后原子写盘。
- Store 对缓存写入使用 trailing coalescing 与最大延迟；纯下载进度等不可持久化更新标记为 `cacheRelevant=false`。

### 3.4 防复发规则

1. 不得根据缺失于某一页、某一范围或某次启动同步来删除缓存消息。
2. 新增 TDLib 删除/历史事件时必须同时覆盖：本地驱逐、永久删除、重复页、空页、同秒 ID、离线启动和恢复在线。
3. 新增高频事件时先判断是否真的改变快照；不要默认调用完整持久化。
4. 快照 schema 必须可迁移、可重建、可清理；中途失败必须 abort 暂存事务，旧快照仍可读取。

## 4. 顽疾二：会话切换、滚动定位与底部回弹

**状态：已修复并形成状态模型。核心提交链：** `a2735e7`、`13a12f7`、`84fb999`、`6123aac`、`5b9dad9`、`a993abc`、`7e7c1c7`、`b909f2a`、`c5d20c0`、`fdd9d27`、`16fd66a`、`aa70921`、`1eb7275`、`1091eee`、`f8b7eb0`、`f3d2884`、`ea0c09b`。

### 4.1 典型症状

- 点击会话后侧栏已高亮新目标，消息区仍显示旧会话；再次点击才正常。
- 进入未读位置时先跳底部、再跳目标，或定位遮罩持续数百毫秒到 8 秒。
- 停在底部时消息、图片或输入框高度变化导致上下轻微回弹。
- 用户向上阅读时，新消息、回复框、搜索预加载或历史 prepend 把视口抢回底部。
- 热切换出现空白帧；用不透明遮罩修复后又产生旧内容遮住新目标、克隆布局失真或动画生命周期悬挂。
- 输入一个字符导致顶层 App、侧栏和完整虚拟列表一起渲染；textarea 同步读写高度产生逐键强制布局。

### 4.2 未奏效或代价过高的实现

- **多个滚动写入者。** Virtuoso、viewport/content ResizeObserver、消息挂载回调、`followOutput` 和多帧 pin loop 同时写 `scrollTop`，彼此触发新的观察者通知。
- **用瞬时 `atBottom` 作为事实。** Virtuoso 在恢复尺寸或挂载新行时可能短暂报告底部，导致本应 detached 的会话被抢回最新。
- **延长遮罩与预渲染。** 通过最长 1.2 秒遮罩和 4000px 顶部预渲染隐藏闪动，实际增加了重新挂载与布局工作。
- **双缓冲/整树常驻。** `a993abc` 的克隆缓冲继续演化后，`7e7c1c7` 尝试常驻最近会话的完整 React 树；它扩大订阅、副作用、焦点、媒体和内存边界，`b909f2a` 将其撤回。
- **把“修正已排队”当“定位完成”。** 过早发布 `aria-busy=false`/positioned 会让动画、性能追踪和下一次操作基于不稳定几何。
- **绝对禁止视觉快照。** `16fd66a` 正确移除了参与切换协议的旧快照，但后续实际性能证明目标列表重测期间仍会暴露空白帧；`f8b7eb0` 重新引入的不是状态快照，而是有严格生命周期的只读视觉桥接。

### 4.3 当前状态模型

- Store 唯一拥有 `activeChatId`/`activeTopicId`。
- App 只维护一个带单调 `requestId` 的 `ConversationScrollRequest`，语义为 `entry`、`latest` 或 `message`。
- 所有入口先解析目标和视口意图，再在同一个同步 React 事务中提交命令与选择；异步历史、已读和缓存工作带 generation，迟到结果失效。
- `useConversationScroll` 是底部跟随唯一写入者。ResizeObserver、总高度变化和消息挂载只能请求合并协调，不能直接竞争 `scrollTop`。
- 底部协调器等待安静帧并做有界最终贴齐；用户向上意图、主/中键控制、detached 模式或 identity/generation 变化立即取消跟随。
- 热会话恢复 Virtuoso `StateSnapshot` 前校验首尾消息和虚拟块身份；输入高度测量每动画帧最多一次，草稿订阅收敛到当前会话/单行。
- 当前切换视觉快照克隆已有消息壳并复制 canvas 像素，放在 closed ShadowRoot 中，`aria-hidden`、`inert`、无 pointer events；目标 viewport ready 后 90ms 释放，最长 1500ms 强制清理，resize/卸载/新事务可中断。它不能读取、修改或决定目标状态。

### 4.4 防复发规则

1. 选中行、标题、消息 ID 必须始终来自同一目标；第二次点击不能成为协议步骤。
2. 一个滚动位置只能有一个写入者；动效只能请求语义目标，不能直接控制虚拟列表几何。
3. `positioned` 只由最终 settlement callback 发布一次；排队的 rAF、ResizeObserver 通知或首次范围回调都不代表完成。
4. detached 会话不能被新消息、媒体 decode、回复框增高、搜索预加载或底部观察者移动。
5. 视觉快照必须非交互、非事实源、有可中断的最大寿命；不得重新引入等待第二次点击、等待网络或无限延长的遮罩。
6. 修改滚动后至少覆盖：首次未读、热切换、底部 append、向上阅读 append、历史 prepend、输入区增高、搜索/置顶/回复跳转、指针/滚轮、中间尺寸增长和 reduced-motion。

## 5. 顽疾三：消息文本选择与局部引用反复失效

**状态：已修复。核心提交：** `6269fc6`、`5a60190`、`7ca6940`、`abc38ca`、`c628e78`、`eb756ea`、`e60de80`。

### 5.1 症状与根因

- 拖选消息文本时，输入框自动聚焦在 80ms 后抢走焦点并清空原生选区。
- 选区可以跨越两条虚拟消息，复制或引用得到错误范围。
- 右键菜单打开、消息更新、Markdown lazy fallback 或元数据布局切换后，浏览器 Range 指向的文本节点被替换，已选文本消失。
- 局部引用只保存显示字符串，没有保留 UTF-16 offset、实体或发送失败语义；消息更新后引用目标与选区失配。
- 为保护选区而暂停所有布局测量只解决一个时机，反而会留下元数据布局不更新。

### 5.2 最终修复技术

- 输入框自动聚焦前检查非折叠原生选区；文本拖选期间不抢焦点。
- 以单个 `.message-rich-text` 为选区边界，根据指针方向把 Range clamp 在同一消息内。
- 右键前把局部引用快照保存为文本、offset 和实体；菜单或消息更新不能丢失该快照。
- 草稿、发送命令和失败重试完整携带 `MessageReplyQuote`；TDLib 报告 quote 失效时区分“重选引用”和“取消回复”。
- 最终不靠暂停 ResizeObserver，而是保持被选择文本节点的 React 身份稳定；Markdown Suspense fallback 可以存在，但普通状态更新不能替换已经解析的节点树。
- 主键点击选区外、切换会话或点击输入框会明确清除选区和 CSS 状态；同一选区内部操作不会误清除。

### 5.3 防复发规则

1. 不得用动态 key、条件 wrapper 或 loading fallback 在普通消息更新时替换 `.message-rich-text` 根节点。
2. 原生选区相关测试必须使用真实鼠标拖动，并在延迟布局/状态更新后再次检查，而不是只用 `Range.selectNodeContents()` 人工造状态。
3. 局部引用必须基于原始消息文本 offset；渲染后的 DOM 文本、搜索高亮或 Markdown 标记不能作为协议 offset。
4. 任何 autofocus、菜单关闭或消息动画都要验证不会破坏有效选区。

## 6. 顽疾四：媒体几何、说明、下载与流式播放

**状态：已修复。核心提交链：** `462a5b0`、`23072e8`、`e019c64`、`26b7cb4`、`6b6ee63`、`1aa9719`、`a73910d`、`934a2ce`、`1ae13ad`、`d935615`、`eac4a73`。

### 6.1 反复出现的错误模型

- 固定列数 CSS grid 无法同时处理横图、竖图、缺尺寸媒体和 2/3/5/7/10 项相册，容易留下空格或把短 caption 收窄成错误卡片宽度。
- 把每个相册子消息的 caption 全部显示在气泡中造成重复与高度膨胀；全部删除又会让查看器丢失原始说明。
- 文件展示名、保存名和 TDLib 本地临时路径混用，导致下载管理器显示错误视频名或生成不可用 Windows 文件名。
- 清理本地缓存后仍复用旧 file state/path，重试继续指向失效资产。
- 流媒体安全窗口固定在开头 8 MiB；长 FLAC 播放位置前进后 Rust 仍拒绝后续 Range，表现为播放到一段后卡住。
- 通用 TDLib bridge 的安全 allowlist 没有放行 cancel，UI 显示已取消但底层下载继续。
- 自动化默认追加 `--mute-audio`，让“测试通过”与真实有声播放脱节。

### 6.2 最终修复技术

- 相册使用确定性 justified mosaic：先把源宽高比 clamp 到 0.72-1.8，再用动态规划按理想行宽成本选择每行 1-4 项；每行完整占满气泡宽度，tile 权重保留相对比例。
- 气泡内只保留紧凑相册网格；每个媒体项的 caption 留在媒体模型中，由全屏查看器按当前项展示。
- 带说明单媒体先根据源尺寸与可读下限计算稳定卡片宽度，窄会话对完整媒体框等比缩放。
- 下载管理器只记录用户主动下载，文件索引随消息增量维护；文件名来自 TDLib remote/local 元数据并经过 Windows 安全规范化。
- 缓存路径失效时先通知 TDLib 删除陈旧本地状态，再允许单次自动恢复，避免无限重试。
- 音视频媒体协议只读取已注册文件的已下载区间；音频播放进度持续回传 Rust，使允许缓冲窗口随 currentTime 前进；MIME 只保留白名单音视频类型。
- `cancelDownloadFile` 通过专门字段校验后进入 Rust allowlist，file ID 必须非零且 cancellation mode 明确。
- 未下载图片可以显示 TDLib 已提供的清晰 preview，同时保留明确 Download 图标；preview 不是可播放媒体，不使用 Play 图标或强制模糊。
- 原生自动化曾改为仅显式参数才静音；随后 `b42ec10` 已整体移除远程调试/开发者自动化入口，真实媒体验收回归原生 smoke 与人工门禁。

### 6.3 防复发规则

1. 媒体布局算法必须是纯函数，并覆盖混合比例、缺尺寸、窄屏、失败态和完整行占用。
2. caption 的协议所有权属于单个媒体消息；气泡和查看器只是不同呈现策略，不能删除源数据。
3. 下载“取消”必须验证 TDLib 请求实际到达，不能只验证按钮状态。
4. 大文件流式测试必须让播放位置跨过初始缓冲窗口，并验证 Range、MIME、暂停/恢复、缓存清理和取消。
5. 自动化的 mute/autoplay 策略必须写入测试前置条件；浏览器 Mock 不能替代真实 WebView2 音频输出。

## 7. 顽疾五：提醒已读状态被本地消费或批量误清

**状态：已修复。核心提交：** `8d4fb0a`、`1afa3fc`、`92c24bc`、`b399bcd`。

### 7.1 反复过程

第一阶段只在本地 Store 中移除已经可见的 mention/reply ID，重启或其他设备仍显示未读。`92c24bc` 随后调用 `readAllChatMentions`/`readAllForumTopicMentions` 持久化，但它在打开会话或阅读一个话题时会一次清除所有提醒，包括用户没有看见的消息。这种“修复持久化、破坏阅读语义”的实现只保留了一个提交。

`b399bcd` 撤掉 bulk-read allowlist，改为由 IntersectionObserver 识别当前聚焦、前台、真实可见的提醒消息，按 ID 批量调用 `viewMessages(force_read=true)`。Transport 处理 `updateMessageMentionRead`，Store 用请求集合、已确认集合和 generation 去重，只有 TDLib 请求成功或更新到达后才移除本地提醒。

### 7.2 防复发规则

1. “进入会话”“跳到消息”和“消息真实可见”是三个不同事件；只有最后一个可以确认提醒已读。
2. 不使用 `readAll*Mentions` 代替可见性语义，除非产品明确提供“全部标为已读”的独立命令并二次确认。
3. IntersectionObserver 还要检查窗口聚焦、document visible、焦点位于当前 conversation，避免后台或被遮挡窗口误读。
4. 本地 UI 只能在后端成功后乐观收敛，并要用 generation 拒绝切账号/会话后的迟到结果。

## 8. 顽疾六：原生上下文菜单与多窗口生命周期

**状态：已修复，仍需真实 Windows 门禁。核心提交链：** `e8ee7cf`、`c21527c`、`56e792c`、`50cff3c`、`c28e006`、`0a22d4e`、`d463ef5`、`2f06ce5`、`6482267`、`91a570e`。

### 8.1 症状与根因

- React 内嵌菜单被 WebView 边界裁剪；原生窗口版又出现首次空白、焦点丢失、圆角/缩放偏差和滚动后残留。
- 每次右键创建并销毁一个 WebView，页面加载、主题、广播握手和窗口聚焦成为高频开销。
- 旧菜单会话的 close/resize 消息可以作用于较新的菜单，形成时序竞争。
- 视频子窗口创建时直接设置 parent/fullscreen/visible，在 Windows 窗口创建与 WebView page load 期间发生死锁或黑窗。
- 所有子窗口共用 `src/main.tsx`，即使只显示菜单也加载主应用、Transport 和大部分依赖。

### 8.2 最终修复技术

- 浏览器回退菜单统一使用纯布局函数处理 viewport clamp、嵌套方向、键盘顺序和 scroll dismiss。
- Tauri 原生菜单改为一个预创建、隐藏复用的 `context-menu-shared` WebView；每次打开只更新物理坐标、逻辑尺寸和 descriptor。
- Rust 保存 active session ID；旧会话不能 finish/resize 当前菜单。前端 BroadcastChannel 也用 session ID 去重 init/close。
- 菜单先 prepare/open 隐藏窗口，React 完成测量后再 show/focus；关闭时 hide 而不是销毁。
- 设置、视频、媒体查看器、上下文菜单分别使用独立 HTML/Vite entry，只加载各自组件与依赖。
- 视频窗口先以 hidden、非 fullscreen 创建；PageLoad Finished 后再设置 fullscreen、show、focus，并移除不必要的 parent 关系；ready 广播重复发送直到收到 descriptor。

### 8.3 防复发规则

1. 原生窗口创建、页面 ready、descriptor ready、首次测量、show/focus、close 必须是显式阶段，不能假设 build 返回即 DOM 可用。
2. 所有跨窗口消息带不可复用 session ID；旧会话不得关闭或覆盖新会话。
3. 高频临时窗口优先复用并隐藏，长生命周期媒体窗口按独立协议关闭；两者不要混用。
4. 子窗口必须有独立 bundle entry；禁止从查询参数分支加载完整主应用。
5. Mock 只能验证协议与 DOM；透明、置顶、物理像素坐标、多显示器和焦点必须在原生 WebView2 验收。

## 9. 顽疾七：性能指标把等待误报为卡顿

**状态：已修复。核心提交：** `84afd39`、`21352ed`、`3b73280`、`1eb7275`、`1e33acb`。

### 9.1 错误模型

- 会话 trace 8 秒未完整结束就记录“8 秒性能问题”，但可能只是历史/后端异步等待、阶段回调缺失或 trace 被新导航替代，主线程并未冻结。
- 固定按 60Hz 估算掉帧，在 120/144Hz 显示器上会低估丢帧，在后台标签或失焦窗口又会把浏览器节流当 UI 卡顿。
- 只记录总 duration，无法区分 JavaScript、样式布局、浏览器呈现、React commit、虚拟列表定位、异步数据和诊断自身开销。
- 每条 layout shift、TDLib update 或性能日志都立即持久化，会让诊断系统成为新的负载。

### 9.2 最终修复技术

- Rust 通过 Win32 `MonitorFromWindow`、`GetMonitorInfoW`、`EnumDisplaySettingsW` 获取窗口当前显示器刷新率；失败时前端用 rAF 校准，最终才回退 60Hz。
- 记录 frame budget、expected/missed frames、visibility、focus、network 和窗口/区域上下文。
- 接入 Long Animation Frame、Long Task、Event Timing、Layout Shift、React Profiler 与会话阶段 mask；脚本归因只保留有界的来源类别、invoker、forced layout 和 pause 信息。
- 会话 trace 分离 visual response、measured frontend work、async wait、main-thread evidence、completed/missing stage。超时且缺少阻塞证据时标记为 incomplete trace 或 backend wait，不再等同 UI stall。
- 性能面板只把 `uiStall=true` 计入界面卡顿，异步慢项单独统计。
- 日志批量发送、布局偏移合并、频谱和 frame sampler 在后台暂停，防止观测反过来改变被观测对象。

### 9.3 防复发规则

1. 不用 wall-clock 总时长直接下“卡顿”结论；必须附带主线程或呈现证据。
2. 性能阈值以当前 frame budget 表达，不硬编码 16.7ms 之外的显示假设。
3. trace 超时要报告缺失阶段，不能把 timeout 当成瓶颈阶段。
4. 新增监控必须有容量、频率和持久化上限，并验证监控开/关对相同操作的影响。

## 12. 动效系统的最终约束

`b90460c` 与 `ea0c09b` 将零散动画收敛为共享 token、`MotionPresence`、`useStableVisibility`、`StableImage`、文档可见性和 reduced-motion 策略：

- 60/120/180/220ms 分别用于原生菜单确认、快速反馈、标准状态和大型表面；业务超时与几何 settlement 不得放入动效 token。
- loading 延迟 140ms 出现，出现后至少保持 320ms；已有结果在分页时继续挂载，避免 loading/empty/result 单帧闪烁。
- 图片只有当前 src 完成 `decode()` 后才淡入；资源切换保留稳定占位几何。
- 连续 Canvas/频谱/视频/性能采样在 document 后台或元素离开视口时暂停。
- `MotionPresence` 的退出内容 inert 且从无障碍树隐藏；重开必须中断旧退出并创建新 session。
- `npm run motion:check` 静态拒绝未使用共享 duration 或动画布局属性的 CSS。

当前普通会话切换允许第 4 节定义的受控视觉快照；它是几何空白的视觉桥接，不是平滑滚动或状态动画。显式远距离消息跳转仍使用独立、有限的 directional snapshot。两者都必须服从 reduced-motion 与最大寿命。
